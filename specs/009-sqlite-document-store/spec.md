# Feature Specification: SQLite JSON 文档存储

**Feature Branch**: `009-sqlite-document-store`  
**Created**: 2026-10-24  
**Status**: In Progress

将配置、数据集划分、实验快照和结果等版本化文档统一保存到 SQLite JSON 字段。保留稳定文档 ID、版本、结构版本、UTC 时间和内容哈希；迁移既有 JSON 文件时不得丢失或静默改变数据。运行环境不依赖 Redis 或 MongoDB 服务。

## User Stories

### US1 — 使用单一数据库保存关系和动态文档 (P1)

用户创建或读取模板、划分、实验快照和结果时，业务服务沿用当前文档仓储契约，文档内容和对应版本元数据共同持久化在 SQLite 中。

**独立验收**：重启应用后可以读取已保存文档；数据库中的文档行包含 JSON 内容，引用标识、哈希和业务 API 返回保持稳定；不启动外部数据库服务。

### US2 — 自动迁移历史文档文件 (P1)

应用首次启动时，将数据目录中既有的版本化 JSON 文档导入 SQLite，并在完成校验后保留源文件备份。

**独立验收**：迁移会核对文件名/文档 ID、结构版本、业务类型、所有者、版本及 SHA-256；重复启动不会重复创建或改变内容；迁移中断或发现损坏时保留源文件且启动失败可诊断。

### US3 — 检测损坏并保护文档身份 (P1)

应用按文档引用读取内容时，验证引用元数据和内容哈希；文档版本不可被不同内容覆盖。

**独立验收**：重复发布相同 ID 和内容是幂等的；同一 ID 或业务版本对应不同内容时报冲突；内容、哈希或引用不匹配时返回存储损坏错误。

## Requirements

- **FR-001**: 版本化文档通过 SQLAlchemy ORM 的 SQLite JSON 字段持久化，并与文档 ID、类型、所有者、版本、结构版本、UTC 时间及哈希元数据共同提交。
- **FR-002**: 当前文档仓储调用方、HTTP API 响应、实验 YAML 导出及划分 JSON 导出保持兼容；业务层不得依赖 SQLite 查询语法或物理存储路径。
- **FR-003**: 首次启动对旧 `documents/<uuid>.json` 文件执行可重试迁移；导入前验证文件名、信封结构、字段类型、引用元数据和原始字节哈希。
- **FR-004**: 对于数据库内已存在的文档元数据，迁移只能补全匹配的空 JSON 内容；发现 ID、类型、所有者、版本、结构版本或哈希冲突时必须停止，不覆盖来源。
- **FR-005**: 所有有效历史文件成功迁入且数据库文档内容完整后，源目录以原子目录改名保留为迁移备份；迁移失败不得删除、改写或覆盖任何源文件。
- **FR-006**: 迁移可重复执行；进程在导入完成、备份改名前退出后，重试结果与单次完成一致。
- **FR-007**: 文档写入只接受有限、可 JSON 序列化的值；非法内容不会影响已存文档。
- **FR-008**: SQLite 是关系型及动态文档数据的唯一活动存储；运行和开发不需要 Redis、MongoDB 或 JSON 文档服务。

## Assumptions

- 现有部署数据目录中的 `documents` 目录是迁移输入；其内容由当前版本的 `JsonDocumentStore` 产生。
- SQLite 的 SQLAlchemy `JSON` 类型提供 JSON 文档语义；暂不依赖特定 SQLite JSONB 版本或原生扩展。
- 已有数据库可能包含文档元数据但尚未包含正文，因此迁移须能够按旧文件 ID 补齐；其他数据库表和业务 ID 不变。
- 迁移备份位于同一数据目录，保留完整原文件以支持人工回退；正常运行路径只读写 SQLite。

## Success Criteria

- **SC-001**: 配置、划分、实验快照和结果的集成流程在 SQLite JSON 内容往返后保持既有 API 行为。
- **SC-002**: 对完整历史数据执行迁移后，所有文档 ID、版本、校验哈希、业务引用和 JSON 内容一致，源文件保留在备份目录。
- **SC-003**: 重复迁移不新增文档，不改变哈希或内容；模拟导入/校验失败后，原始 JSON 文件仍可用于重试。
- **SC-004**: 测试在临时 SQLite 和临时目录中运行，不依赖 Redis、MongoDB、GPU 或外部服务。
