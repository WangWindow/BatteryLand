# BatteryLand Constitution

BatteryLand 是面向电池数据治理、健康状态预测与迁移学习的在线实验、管理和可视化平台。
本宪章依据当前开发要求及 `temp/origin_docs/` 中的《功能需求.md》《架构设计.txt》
和《前端设计.pdf》制定。以下条款已固化必要约束，不以临时资料目录始终存在为前提。
初始资料只用于理解基础架构与需求，不冻结其中的技术和模块划分；具体功能以开发过程中
确认的规格文档为准。本项目采用面向 AI 编程的 SDD（规格驱动开发），以 TDD 驱动行为实现，
以轻量 DDD 划分职责。文中的“必须”“禁止”是验收要求；明确标注的“默认”允许通过
有依据的设计决策调整。

## Core Principles

### I. 明确所有权与前后端分离

- 当前主要交付后端 API、业务服务、持久化及专业功能接入。前端技术栈和视觉规范
  是协作边界；每个功能的实际交付范围必须在规格中写明。
- 前端独立组织、构建和运行，通过公开 API 与后端通信；负责页面、交互、展示状态
  和浏览器可视化，不直接读取 SQLite、JSON 文件、实验目录或训练进程。
- 后端负责权威业务校验、资源与状态管理、业务流程协调、数据访问和错误映射；
  领域层表达业务不变量，应用服务协调具体用例，基础设施实现存储和外部调用。
  Router/Controller 不承载持久化细节，Mapper/Repository 不承载业务流程。
- 《架构设计.txt》“功能部分”的训练框架、组件上传与预览、差异分析、实验调度
  及绘图能力由其他贡献者提供；后端必须通过约定接口接入，禁止在服务层另写一套实现。
- 专业模块负责算法、训练执行、设备调度策略及专业结果计算；前端负责浏览器内图表交互，
  后端负责传递规范化数据和调用功能模块。责任划分必须落实到接口及验收归属。

理由：后端、前端和专业功能可以独立推进，避免业务接口与训练内部实现相互绑死。

### II. SDD 驱动的简洁实现与渐进交付

- 规格先于实现：每项业务变更必须有可观察的验收条件，计划和任务必须追溯到对应规格。
  AI 必须在已确认范围内实现，不得自行补充产品行为、改变架构或以代码反向替代规格。
  发现需求矛盾时先记录并解决规格差异，再继续受影响的实现。
- 优先复用标准库、现有依赖和框架能力；新增抽象必须对应真实复用、稳定契约或替换边界。
  禁止仅为透传增加辅助层、为少数字段构建通用引擎或为假想需求引入基础设施。
- 入口保持简短；函数围绕一个明确职责组织，使用可读的控制流、领域命名和显式依赖。
  错误必须在负责的层处理，禁止静默吞错或以假成功掩盖失败。
- 先确认目标、调用链和验收方式，再按可独立验证的步骤交付完整功能。
  重写必须保留约定行为，清除范围内已被替代的路径并同步调用方。
- 每次变更必须保持差异聚焦，保留用户已有修改；禁止顺带格式化整个仓库、改造无关模块
  或修改第三方源码来绕过接入问题。

### III. 显式契约与可替换集成

- 前后端必须以版本化 API 和 OpenAPI 定义交换数据；请求、响应、校验错误、分页、
  状态及日志事件必须有明确结构，禁止依赖后端内部对象或文件布局。
- 专业功能必须先定义所需的最小接口，再实现适配器。业务服务依赖这些接口，
  不直接引用第三方模块的内部包、全局注册表或任意脚本。
- 适配层负责外部配置、结果、异常及进程状态的转换；专业功能的核心实现与升级由其所有者负责。
  接口缺失必须记录为协作依赖，不得以永久模拟实现冒充已接入能力。
- Git 子模块必须固定到明确提交，并记录兼容接口和运行环境。
  不得在普通业务变更中隐式升级子模块或依赖其未提交修改。

### IV. 单一事实来源与可迁移存储

- 结构化实体、关系、索引和可查询状态使用 SQLite，并通过 ORM 访问；配置、划分、扩展指标等文档数据
  当前使用本地 JSON 文件，通过独立文档仓储访问，未来替换为 MongoDB。
- 同一业务字段必须有明确的权威存储。禁止应用层同时维护 MongoDB 与 JSON 的双份权威副本；
  SQLite 中的摘要或索引必须能由其来源重建。
- 文档契约必须使用应用生成的稳定标识、明确的结构版本及可序列化类型。
  业务层不得暴露 MongoDB 专属标识、查询表达式或 JSON 文件路径。
- 存储实现必须保证各自边界内的一致性；跨 SQLite 与文件的操作必须定义失败补偿或恢复步骤，
  禁止将两个独立写入描述为同一原子事务。
- 后续迁移到 MongoDB 必须保持仓储行为与 API 契约，并验证文档数量、标识、引用和内容一致。
  API、Service 与前端不得因存储实现替换而重写业务规则。

### V. 可追溯实验与真实展示

- 实验必须关联稳定 ID、配置快照、数据集与划分版本、专业模块提交或组件版本、随机种子、
  实际设备、状态、时间和产物引用；已有运行记录不得随模板修改而改变。
- 后端负责记录和协调生命周期，专业模块负责执行与调度。
  启动、停止、失败和重启后的状态核对应有明确契约；停止请求被接收不等于进程已经停止。
- 显式设备选择必须原样传递；`auto` 的解析属于调度模块，后端必须记录它返回的实际设备。
  设备不可用时必须报告失败，禁止静默换卡或改用 CPU。
- 数据划分必须防止同一电池及其派生样本跨训练、验证、测试集泄漏；指标必须保留名称、
  单位、聚合粒度、适用样本和计算条件，比较结果必须注明条件差异。
- 缺失真值、缺失指标、不同电池集合和自定义指标必须被显式表达；禁止补零、伪造结果
  或混淆窗口级与电池级指标。未提供不确定性估计时不得绘制虚构置信区间。

### VI. 克制一致的专业界面

- 前端必须使用 React、shadcn/ui 与 Tailwind CSS，采用稳重、低装饰的科研工作台风格。
  页面围绕数据、配置、执行监控和结果比较组织，优先保证信息层级和操作效率。
- 色彩、间距、字体、圆角、图表配色和状态表达必须来自统一设计变量。
  禁止以大面积渐变、霓虹色、装饰性动画或重复卡片替代信息组织。
- 控件必须匹配数据类型，长表单分组，危险操作有明确反馈；键盘操作、焦点、标签、
  加载、空数据、错误和禁用状态必须可辨识，状态不得仅依靠颜色表达。
- 图表必须支持浏览器内交互，并标注坐标、单位、图例、样本范围和缺失数据。
  同一数据序列在不同视图中使用稳定颜色；后端提供数据契约，绘图能力按协作边界接入。

### VII. TDD 与可核验的交付

- 新增或修改业务行为、修复缺陷必须执行“红 → 绿 → 重构”：先从规格验收条件编写测试，
  运行并确认因预期行为缺失而失败，再写最小完整实现，最后在测试保护下改善结构。
  导入错误、环境缺失或无关断言失败不能作为有效的“红”；禁止写完实现后补测试冒充 TDD。
- 测试必须验证可观察行为、回归或边界契约，禁止只复述实现、检查私有函数布局
  或为覆盖率数字增加无意义断言。新测试放在独立测试目录。
- 业务行为变更必须覆盖相关正常路径、关键失败路径和状态变化。
  纯重构先运行已有相关测试建立基线；若行为保护缺失，先补充有效测试再调整实现。
- 持久化、API 或专业模块契约变更必须有相应集成或契约测试；
  仅文档变更执行内容与差异检查，不人为增加行为测试。
- 验证从受影响范围开始，再执行相关套件及格式、静态和构建检查。
  通过后只有新变更、失败或未解决问题才触发重复或扩大验证。
- 完成报告必须写明实际检查、结果及未验证边界。构建成功不能代替页面交互验证，
  模拟器通过不能声称真实 GPU 训练或外部模块接入已经通过。

## 技术栈与架构约束

### 技术基线与模块布局

- 后端使用 Python 与 FastAPI，前端使用 React + TypeScript + shadcn/ui + Tailwind CSS。
  TypeScript 启用严格类型检查。Python 版本以 `pyproject.toml` 为准，当前声明为 `>=3.14`；
  接入专业模块前必须核对其解释器及依赖兼容性，不得未经说明改变运行版本。
- Python 项目默认沿用 uv 管理。前后端必须具有独立依赖声明、配置入口、启动和检查命令；
  同仓库、同域部署或开发代理不改变前后端的责任边界。
- 保持主项目后端包 `src/batteryland/`，前端源码独立放置于 `frontend/`；
  专业模块沿用已有 `src/deeplatform/` 子模块边界，新增子模块的位置由接入计划明确。
  禁止把前端代码、实验产物或专业算法混入后端业务包。
- 后端采用轻量 DDD 的模块化单体；分层围绕业务边界建立，保持清晰的单向依赖。
  具体上下文、目录和数据对象在功能计划中确定，不按早期草图机械拆出模块。
- 训练及其他长任务必须交由专业执行模块或独立进程运行，禁止阻塞 FastAPI 事件循环。
  普通同步文件和数据库 I/O 必须使用合适的同步执行边界，不能仅用 `async def` 包装阻塞工作。
- 默认开发环境只要求本地文件系统、SQLite 及前后端运行环境；
  MongoDB、Redis、MySQL、独立消息队列和容器集群不得成为基础开发的必需依赖。
  Redis 不是预定架构组成部分；新增基础设施必须由实际规格需求驱动，
  并在计划中说明简单替代方案、收益和环境成本。

### 轻量 DDD 与依赖方向

| 层 | 职责与对象 | 依赖边界 |
| --- | --- | --- |
| 接口层 `interfaces/api` | FastAPI Router、请求/响应 DTO、HTTP 与事件协议转换 | 调用应用用例，不直接操作 ORM 或文件 |
| 应用层 `application` | 用例服务、流程协调、事务边界、输入输出对象、能力接口 | 依赖领域及其消费的接口，不依赖具体基础设施 |
| 领域层 `domain` | 实体、值对象、业务不变量、必要的领域服务及仓储契约 | 不依赖 FastAPI、Pydantic、ORM、文件系统或专业模块 |
| 基础设施层 `infrastructure` | ORM 映射、仓储实现、迁移、JSON 存储、外部模块适配器 | 实现内层接口，转换外部数据，不承载业务决策 |

- 运行调用从 API 进入应用用例，再访问领域行为及仓储或专业能力接口；
  基础设施通过依赖注入实现这些接口。装配入口负责选择具体实现，禁止内层反向导入实现类。
- 仓储接口归属于使用它的领域或应用边界，持久化实现位于基础设施层；
  Mapper 如确有需要，只负责领域对象与持久化对象的转换，不能成为独立业务服务。
  不为每个类创建接口，不预建通用 Repository 基类和无实际用途的工厂。
- 必须区分领域实体/值对象、API DTO、ORM 持久化模型与外部模块对象。
  ORM 模型不得作为领域模型或 API 响应向外泄漏；必要转换必须显式且局部。
  允许复用无框架依赖且语义相同的简单值类型，禁止机械复制多套无差别字段。
- 业务不变量在领域层集中表达，应用服务编排用例，仓储只读写数据；
  禁止把规则同时写入 Router、Service 和 ORM 事件。简单 CRUD 可由应用服务与仓储完成，
  只有真实业务规则需要时才引入聚合、值对象或领域服务。
- 专业模块通过适配器隔离外部概念，领域与应用层只认识本项目的最小契约。
  默认不引入微服务、CQRS、事件总线、分布式事务或完整事件溯源；
  只有已确认规格证明必要时才扩展，避免用 DDD 名称增加模块耦合与复杂度。

### ORM 与事务职责

- 关系型访问默认采用 SQLAlchemy 2.x ORM，结构迁移采用 Alembic；
  SQLite 开发先使用同步 Session，不为形式上的全异步引入额外驱动和并发复杂度。
  JSON 以及未来 MongoDB 走文档仓储，不强行套用关系型 ORM。
- ORM 映射、Engine、Session 配置、SQL 查询与迁移位于基础设施层；
  API 和领域层禁止直接执行 SQL。特殊查询确需 SQLAlchemy Core 或参数化 SQL 时，
  必须留在仓储实现内，并说明 ORM 表达不足的具体原因。
- 应用用例确定事务范围，基础设施提供会话与事务上下文，Repository 不自行提交。
  成功时统一提交，异常时回滚并清理；禁止全局共享 Session、跨并发任务复用 Session
  或在请求结束后继续使用其延迟加载对象。会话并发约束参见
  [SQLAlchemy Session 文档](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)。
- Alembic 迁移必须审阅生成内容，在临时 SQLite 上验证升级及历史数据保留；
  涉及 SQLite 不支持的结构变更时使用其
  [批量迁移机制](https://alembic.sqlalchemy.org/en/latest/batch.html)。
  不得在生产启动时用 `create_all` 或删除重建数据库替代版本迁移。
- 数据约束、唯一性、索引及领域规则必须职责互补：领域给出业务语义，数据库守住并发下的
  最终完整性，仓储将约束失败转换为明确错误；禁止依赖前端校验或“先查后写”保证唯一性。

### 编码、注释与文档

- 标识符统一使用英文，使用领域含义明确的完整命名。
  Python 模块、变量和函数用 `snake_case`，类用 `PascalCase`，常量用 `UPPER_SNAKE_CASE`；
  TypeScript 变量、函数和 Hook 用 `camelCase`，组件和类型用 `PascalCase`。
- Python 使用四空格缩进、100 字符行宽及 Ruff 统一格式与静态检查；
  TypeScript/TSX 使用两空格缩进，通过 Prettier 统一格式、ESLint 检查代码。
  导入按标准库、第三方、项目代码分组，禁止通配符导入；不手工维护与格式工具冲突的排版。
- Python 公共接口、跨模块函数及数据边界必须有类型标注，以 mypy 检查主项目代码。
  TypeScript 禁止无依据的 `any` 和非空断言；外部未知值先收敛为可验证结构。
  忽略类型或 lint 规则必须局部使用，并解释具体原因。
- 请求、配置、文档及外部结果在入口进行结构校验，业务不变量由领域层判定，应用服务协调执行；
  前端校验用于交互反馈，不能替代后端权威校验。禁止 `eval`、不安全 YAML 加载
  或在请求校验过程中执行用户上传的 Python 源码。
- 前端页面负责组合视图，组件负责展示与交互，Hook 负责共享状态和行为，
  API 客户端统一处理请求、错误与契约类型；禁止每个页面自行复制请求和错误处理逻辑。
- 新代码注释和 docstring 默认使用英文，仓库治理、需求和设计文档默认使用中文。
  注释解释意图、约束、单位、状态或生命周期，不逐行翻译代码，不保留注释掉的旧实现。
  公共接口及非显然契约使用简洁 Google 风格 docstring，只说明有意义的参数、返回和异常。
- TODO 必须附具体问题及可追踪任务或明确的解决条件；行为变化时同步更新相关注释和契约。
  README 保持项目介绍、使用入口和技术信息简洁，维护过程记录放入对应设计或贡献文档。

### API、持久化与专业功能接入

- API 默认使用 `/api/v1`，JSON 字段使用 `snake_case`；前端契约类型保留接口字段名称。
  同步 JSON 响应统一为 `code`、`message`、`data`，成功 `code=0`，失败使用契约定义的
  非零数值码并保留正确 HTTP 状态；禁止通过一律返回 HTTP 200 隐藏错误。
  文件下载和日志流使用各自明确的协议，不强行套用普通 JSON 响应封装。
- OpenAPI 是前后端 HTTP 契约的依据；接口变更必须同步消费者类型、样例及相关契约测试。
  日志与状态事件必须定义实验 ID、顺序或游标、终止和重连语义。
  异常映射集中处理，对外错误可定位，对内保留诊断信息，禁止暴露密钥和内部堆栈。
- SQLite 必须显式启用外键约束，通过 ORM 和事务维护关联实体，使用版本化结构迁移；
  禁止通过删除本地数据库代替迁移。大体积原始数据、日志、模型权重保存在文件系统，
  数据库记录可校验的相对引用及必要元数据，不将二进制产物塞入 JSON 文档。
- JSON 仓储必须集中管理数据根目录、文档 ID 与路径映射、`schema_version` 及 UTC 时间戳。
  写入采用同目录临时文件与原子替换，读改写整体受锁保护；默认只允许一个后端进程写入。
  增加写入进程前必须实现并验证跨进程协调，不能仅依赖进程内锁或约定不并发。
- SQLite 与文档文件联合创建、更新或删除时，Service 必须定义写入顺序、失败可见状态
  和可重试的补偿或恢复动作；测试至少覆盖“文件已写而数据库失败”及反向失败场景。
- MongoDB 迁移必须复用同一仓储契约测试，并包含可重复执行的导入、校验和回退方案；
  仅在切换阶段明确双读或复制策略，正常业务路径不得长期依赖双写。
- 专业接口必须明确输入配置、输出结构、能力版本、异常、运行标识及启动/停止/查询语义。
  后端处理业务状态和持久化，调度策略、设备分配与训练实现留在专业模块。
  组件目录、配置表单元数据及结果字段优先复用模块提供的接口，不在后端硬编码另一份清单。
- 外部模块尚未交付时，可用明确标识的测试替身推进契约验证；运行界面必须呈现能力未接入，
  不得将测试结果写成真实实验结果。测试替身不得发展成第二套生产实现。
- 上传文件必须校验类型、大小和目标位置，禁止路径穿越。
  Python 组件的执行必须限定于约定的可信执行边界或隔离环境，上传校验不得启动训练。
  运行参数、数据目录和允许的前端来源通过后端集中配置，禁止提交密钥或硬编码机器绝对路径。

### 视觉与交互基线

- 默认采用浅色工作台：页面背景 `#F8FAFC`、内容表面 `#FFFFFF`、主文字 `#0F172A`、
  次文字 `#64748B`、边框 `#E2E8F0`、主操作 `#1E40AF`。
  成功、警告、失败分别采用 `#15803D`、`#B45309`、`#B91C1C`，并配合文字或图标。
  颜色必须映射到 shadcn/ui 语义变量；禁用、浅色和交互状态需分别校验可读性。
- 使用固定侧边导航、清晰的页面标题与操作区、主体数据工作区；复杂筛选置于工具栏，
  次要详情用页签、抽屉或详情面板呈现。页面只突出一个主要操作，危险操作与主要操作分开。
- 使用 4/8 像素间距基准、统一控件高度和圆角；采用系统无衬线字体，数值展示按需使用等宽数字。
  优先复用 shadcn/ui 的表格、表单、对话框和提示能力，避免重复容器和装饰性阴影。
- 布尔值用开关或复选框，枚举用选择控件，数值标明单位与范围；
  实验配置按数据、模型、训练和设备等业务分组，专业字段由契约元数据驱动，
  高级参数渐进展开，不把训练框架内部细节直接倾倒给使用者。
- 数据表支持与实际规模相符的检索、筛选和分页，图表支持必要的缩放、悬停和图例选择。
  指标排序、单位和精度跨视图一致；缺失值展示为不可用并说明原因。
  结果比较必须清楚标识实验、数据集、源域和目标域；图表代码或绘图能力按外部功能契约接入。
- 页面必须覆盖窄屏、长文本、大数据列表、加载失败和空结果；
  若后续实现前端，验收必须包含真实页面交互与状态恢复，不能仅验收截图或构建产物。

## 开发、测试与 Git 工作流

### 面向 AI 编程的 SDD 与协作

1. 开始前读取宪章、仓库指令、Git 状态、相关实现和检查命令；确认当前分支，
   区分用户已有修改与本任务变更，明确交付目标及后端、前端、专业模块的责任人或归属。
2. 新功能按 `spec.md → 必要澄清 → plan.md 与契约/数据模型 → tasks.md → TDD 实现 → 验收`
   推进。规格必须包含范围、可观察验收、异常情形和外部能力依赖；
   计划说明 DDD 职责、ORM/文档存储边界及契约，任务按可验证的业务行为拆分。
   小型修复可使用简短变更说明与验收条件，但不得跳过行为变更的测试先行。
3. 涉及专业模块时先对齐最小契约、能力就绪情况和兼容版本；
   接口适配、业务实现和算法实现分别由对应所有者承担。
   外部能力缺失时继续完成可独立验证的后端工作，并记录剩余接入条件。
4. AI 按任务逐项执行红、绿、重构，先读相关实现与契约再修改，保持每一步差异可审阅；
   不得因易于生成而扩大范围、堆叠抽象或重写外部所有者的功能。
   规格发生实质变化时先同步规格、计划、契约及受影响任务，禁止只改代码造成文档漂移。
5. 维护验收条件、测试与实现任务之间的对应关系，在既有任务记录中保留关键失败/通过证据、
   决策、进展和下一步。Spec Kit 正式规格属于项目交付文档；
   个人计划、临时探针和过程草稿不进入提交。
6. 完成后清理本任务临时产物，审阅最终差异，报告实际交付、检查证据、外部依赖缺口
   及 Git 状态；没有执行或无法执行的检查必须明确说明。

### 测试层次与关键场景

- 后端以 pytest 为基础：单元测试验证业务规则和状态机，API 测试验证请求校验、响应及 HTTP
  语义，集成测试使用临时 SQLite 与临时文档目录，专业模块通过接口契约测试验证。
- 领域测试不启动 FastAPI、数据库或训练框架；应用测试可用窄接口的测试替身；
  ORM 仓储测试使用真实临时 SQLite，验证映射、事务回滚、约束与迁移。
  测试替身不能代替基础设施集成测试。
- 必须覆盖被本次变更影响的数据 CRUD、重复提交、配置错误、文档损坏、写入失败和引用完整性；
  涉及实验时覆盖启动、停止、失败、状态核对及日志终止。断言面向支持的公开接口。
- JSON 仓储必须验证原子写入、并发保护、损坏文档错误及跨存储补偿；
  未来 MongoDB 实现必须通过同一行为测试，而不是另定义一套语义。
- 科学结果相关变更必须覆盖划分泄漏、缺失真值、自定义或缺失指标、不同电池集合、
  指标单位和聚合粒度；不得只以曲线“能画出来”作为正确性证据。
- 日常后端测试默认不依赖 GPU、完整数据集或外部服务；使用小型固定数据和受控执行替身。
  涉及真实专业模块接入的变更另执行针对固定版本的最小冒烟验证，记录运行环境；
  环境不可用时明确标记该验证缺口，不将替身验证等同于真实接入成功。
- 当前端进入交付范围时，使用 Vitest 与 React Testing Library 验证交互行为，
  关键业务闭环使用 Playwright 或有记录的浏览器验收；后端负责 API 契约证据，
  前端负责用户交互证据，专业模块负责算法与执行证据，跨边界场景联合验收。
- 不统一设置脱离风险的覆盖率门槛；重要业务和失败边界必须有行为证据，
  纯文档、格式与无行为变化的静态展示调整使用相称检查，不人为编造失败测试。
  一旦改变交互、业务规则或数据行为，必须恢复 TDD 红绿重构循环。

### 完成与集成门槛

- 后端代码变更必须通过受影响的 pytest 套件、Ruff 格式检查与 lint、mypy 类型检查；
  包结构、依赖或入口变化时追加构建和启动验证。第三方子模块不纳入主项目格式化扫描。
- 前端代码变更必须通过格式、ESLint、TypeScript 类型检查和构建，
  并执行与变化相符的组件或页面交互验证。只修改后端时不强制构建未受影响的前端。
- API、数据结构、持久化和专业模块契约变化必须同步对应文档、迁移及消费者验证。
  模板中标为可选的测试任务不豁免本宪章规定的 TDD 和行为验证。
- 业务任务完成必须能追溯到规格验收条件，并具有实际执行的预期失败、通过及相关回归证据；
  无行为变化的重构须保留前后通过的基线，不得将尚未接入的专业能力标为完整交付。
- 检查工具尚未配置时，首次引入对应实现必须同时建立必要检查入口；
  禁止将没有运行的命令写为通过。无关基线失败必须与本次失败分别报告。
- 性能结论必须有可比较条件下的代表性测量；无测量则只报告实现变化。
  完成时必须删除本任务的临时追踪和一次性产物，保留有效日志、测试及必要运行资源。

### Git 分支、提交与集成

- 默认在当前检出目录工作，复用适合本任务的分支；新功能遵循 Spec Kit 的
  `编号-英文短名` 短期分支命名，独立修复或文档任务可用 `fix/英文短名`、`docs/英文短名`。
  分支型任务在修改前建分支，不为小任务额外引入 worktree；合并目标以仓库实际主分支为准，
  当前主分支为 `main`。
- 仅在用户授权提交或会话已有同等授权时提交；合并、推送、发布和历史重写分别遵循授权范围。
  未获授权时交付经过验证的工作区修改，禁止因完成开发自行提交或推送。
- 暂存前审阅差异，只暂存本任务明确文件；禁止覆盖用户暂存区、回滚用户修改或强制添加忽略文件。
  尊重仓库既有测试与锁文件策略；依赖变更必须同步已跟踪的相关锁文件，
  不得把其他项目的忽略策略照搬进来。
- 提交头使用英文 Conventional Commits，例如 `feat(api): add experiment endpoints`；
  scope 对应实际模块。较大变更的正文说明问题、最终变化、影响及实际验证；
  禁止记录未执行检查，禁止以 WIP 或每次工具调用拆分提交。
- 小型完整变更保持一个提交；大型变更仅按可独立审阅且中间状态可用的结果拆分。
  子模块自身变更与主仓库指针更新分别审阅，主仓库必须固定已存在的模块提交。
- 获得本地集成授权后优先快进合并；如仓库要求 PR 或保护分支，按其规则执行。
  禁止为制造干净历史而重置或强推；只有确认集成完成才删除对应任务分支。

## Governance

- 本宪章是项目架构、编码、注释、协作、Git 和质量检查的治理依据。
  原始需求和架构草图是参考；具体功能、接口和协作边界以开发过程中确认的最新规格为准，
  规格必须符合宪章。涉及硬性原则的冲突先修订宪章，不能由局部计划静默覆盖。
- 初始资料中的 MySQL、MongoDB/Redis、数据库与 JSON 同步双写，以及具体模块命名
  不构成固定要求；当前采用 SQLite + SQLAlchemy ORM、JSON 文档仓储和轻量 DDD。
  Redis 可以完全不引入，未来是否新增组件由规格和设计决策确定。
- 每份实现计划必须包含 Constitution Check，核对前后端职责、外部功能所有权、
  DDD 依赖方向、ORM 与数据对象边界、类型与契约、存储一致性、界面规范、
  SDD 追溯、TDD 验证方案和变更范围；代码审阅或 PR 必须再次核对。
- 硬性条款的例外必须在实施前记录适用范围、必要性、替代方案和退出条件，
  并取得项目维护者明确同意；常规实现选择在既有边界内自主处理，不重复请求确认。
- 修订必须说明动机、受影响原则、迁移或协作影响及验证方式，由维护者确认后生效。
  已批准的会话要求可直接落实为修订；重大职责和技术栈变化不得仅藏在代码或局部文档中。
- 宪章采用语义版本：不兼容的原则删除或重定义升主版本，新增或实质扩展规则升次版本，
  不改变语义的澄清和修正升修订版本。首次确立完整规则使用 `1.0.0`；
  该版本与应用程序版本独立。
- 首次批准日期保持不变，每次有效修订更新 Last Amended；日期统一使用 ISO 格式。
  规格、计划、任务与后续实施命令在运行时读取本宪章；审阅用 Sync Impact Report
  属于临时材料，提交修订文件前必须移除，治理条款本身保留。
